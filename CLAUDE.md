# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**The real product is the `my-old-space` framework** (a retro-desktop-styled web desktop / form engine, installed from GitHub: `github:anfy1284/my-old-space`, living in `node_modules/my-old-space/`). This repo — a hotel-booking application ("Wonunger") — is a **reference application used as a testbed to drive framework development**: you extend the booking app, the gaps and bugs it exposes get fixed *in the framework*, and that is the point of the work.

Practical consequence: editing `node_modules/my-old-space/` is the **main activity, not a workaround**. When the booking app hits a limitation or a bug, the fix almost always belongs in a framework base class (so every app benefits), not in app-level code. Treat a local patch in `apps/` as a smell — find the root cause in the framework. (Caveat: `scripts/update-my-old-space.cmd` reinstalls from GitHub and overwrites local framework edits, so framework changes must eventually land upstream in the `anfy1284/my-old-space` repo.)

The most authoritative docs live inside the framework package and should be consulted for non-trivial work. They are **far more detailed than this CLAUDE.md** (which is only a high-level entry point) and currently describe **both the framework and this wonunger project** (the user plans to split them by concern later). They also ship with the framework package, so they apply to its own repo / other consumers too:
- `node_modules/my-old-space/ИНСТРУКЦИИ_ДЛЯ_AI.md` — coding rules, ~150-item anti-pattern catalog, ~128-item self-check checklist, deep i18n/UI/DB specifics (Russian). **Not auto-loaded, but read it proactively at the start of any non-trivial code/framework task — don't wait to be told.** It has outgrown a single Read (~260 KB — over the 256 KB limit): read it in chunks (`offset`/`limit`), starting with sections 1–3 (rules) and grepping section 4 (anti-patterns) / 5 (checklist) by topic.
- `node_modules/my-old-space/АРХИТЕКТУРА_ПРОЕКТА.md` — full technical architecture reference: classes, methods, call chains, protocols (Russian). It's large (~450 KB, 50+ sections) — **consult the relevant section on demand (grep/read by topic); do NOT read it whole every session.**
- `FRAMEWORK_SETUP.md` (repo root) — bootstrap/deployment steps.

**Maintenance triggers (user commands, in Russian):**
- **«обнови инструкцию»** (or «дополни инструкции») → immediately review the *entire* current dialog, find your own mistakes and any newly-learned rules, and update these two framework docs accordingly — rules/anti-patterns/processes go in `ИНСТРУКЦИИ_ДЛЯ_AI.md`, technical structure (classes, methods, call chains) goes in `АРХИТЕКТУРА_ПРОЕКТА.md`, removing duplication between them. - **«сначала прочти инструкции»** → just an explicit re-read command; reading `ИНСТРУКЦИИ_ДЛЯ_AI.md` is already the default above. On this command also pull in the relevant `АРХИТЕКТУРА_ПРОЕКТА.md` sections for the task at hand.

## Database

Sequelize ORM against **PostgreSQL** (the active dialect). `dbSettings.json` selects the dialect; `dbSettings.postgres.json` holds credentials. Both are git-ignored. The schema is *not* migrated by hand — the framework reads every `apps/*/db/db.json` plus the framework's own model defs, merges them, and creates/syncs tables on startup. Seed data comes from `apps/*/db/defaultValues.json`.

Key DB conventions (violating these breaks things silently):
- **A `db.json` key starting with `//` is a comment, not a field** — JSON has no other way to annotate a schema, and the convention was already in use around `entityConfig`. Comment keys are stripped once, in `collectAllModelDefs`, because the definitions are walked by **two** independent loops (runtime `generateModelsFromDefs` and the **migration's** `createDB.defineModels`): a skip in only one leaves the other turning the comment into a typeless column, which brings the whole server down at startup.
- **Never declare a `UID` field in `db.json`.** The primary key is a string `UID`, injected centrally by `events_handler.js#onModelsPostCollect` before `sequelize.define`. Adding it manually, or adding any other `primaryKey`, conflicts with the injection (Sequelize will otherwise invent a phantom `id` column).
- **Entities auto-get a `number` requisite + autonumber, documents also a `date`, and `name` is the computed presentation.** Any model with `entityConfig.entityType` (document/directory/catalog) systemically gets a string `number` field + `default.autoNumber` on it — like UID, injected by `drive_root/db/entityNumber.js` at migration (root `events_handler.js`) and runtime (`globalServerContext.collectAllModelDefs`); **documents additionally get a `date` field** (DATE) + `default.documentDate` (empty date = now on create; never touched on update) via `drive_root/db/entityDate.js`, same two injection points. Never declare `number`/`date`/`default.autoNumber` manually; manual entry is preserved. In hand-written layouts add `number`/`date` fields explicitly (custom layouts get no auto-additions). The `name` field is the **presentation** (display string), filled on every save by a builder registered via `entityHooks.registerPresentation(table, fn)` in the app's `init.js` — `applyPresentation` runs in the `dbGateway` middleware after autonumber. For bookings: `name = number + client + dates`; invoices: `number + client + date`; price lists: `number + hotel + date`. Anything needing the bare number (invoice "Nr.", etc.) must read `number`, not `name`. **Raw-SQL seeders** (`tmp/generate_demo_base.js`, `defaultValues.json`) bypass these hooks — set `number`/`name`/`date` there explicitly. Record-vs-list windows differ: `saveLayout` takes `recordCaption` (singular title + presentation) / `appCaption` (plural list title) and `formIcon`/`listIcon` (document vs journal icon by `entityType`); entity record windows and lists open maximized by default — don't hardcode `windowState`.
- **A document's point in time is `(date, seq)`, and `seq` is injected too.** `drive_root/db/entityMoment.js` gives every `entityType: "document"` a `seq` (BIGINT, NOT NULL, empty = 0) plus the `default.documentSeq` hook and a `(date, seq)` index, at the same two injection points as `number`/`date`. Never declare `seq` in `db.json`. The value comes from the PostgreSQL sequence `document_moment_seq`; it is assigned on every create and re-assigned **only when `date` changes** — an ordinary save must not silently move a document to the end of its day. Order documents by the tuple (`WHERE ("date","seq") > (:d,:s)`), never by `date` alone or by `createdAt`. The sequence value is data: `entityMoment.prepare` runs at startup and after a full restore, backfilling rows that arrived past the gateway (RAW restore, raw seeders) and raising the counter to the max `seq` in the data — without it, restored and new documents collide on moments and the order breaks silently. Spec: `tmp/ТЗ_ПРОВЕДЕНИЕ_ДОКУМЕНТОВ.md` §4.
- **Posting is a core mechanism, declared in `entityConfig.posting`** (`drive_root/db/posting.js`; full reference: section 73 of `АРХИТЕКТУРА_ПРОЕКТА.md`, spec `tmp/ТЗ_ПРОВЕДЕНИЕ_ДОКУМЕНТОВ.md`). An app writes **only** a posting handler (a named function via `entityHooks.register`) and **never** an unposting one: movements belong to the document (`recorderTable`/`recorderUID`) and the core removes them itself, so the two can't drift apart. Consequences that are easy to get wrong: posting is **always deferred** — the command enqueues (`posting_queue`) and wakes the runner (scheduler task `core.postingQueue`), the answer arrives as a notification; a form save enqueues only **after** its tabular sections are written (`context.deferPosting` on the header + `dbGateway.enqueueAfterSave`) — enqueueing on the header write let the handler post empty rows (16.10.2026); the handler must write through `ctx.dbGateway` (transaction + "the mechanism is writing" mark), never the bare gateway, or the document re-enqueues itself forever; `postingState` is written **only on transitions** (the first failure sets `error` once — that is what makes endless retries harmless to the immutability lock and the audit log), and the error text lives in the queue row, not in the document; re-posting must never change `date`/`seq` — the cascade terminates only because it moves forward in time; **a posting handler must be idempotent** — posting is repeatable by nature (cascade, queue retry, bulk re-posting), so movements get rewritten while every one-time side effect (the print archive, the "issued" stamp) is guarded by the *fact* having happened (`documentArchive.exists`), never by the document's state, and a value a repeat could shift is not taken from the clock at all (an invoice's `issuedAt` **is** its `date`, § 14 Abs. 4 Nr. 3 UStG); **unposting is allowed by default** (`unpost` absent → allowed, `false` → forbidden, a list → only from those states — asked via the single core function `posting.canUnpostFrom`), a document that cannot be unposted does **not** get "post and close" on its OK button, and the **confirmation belongs to the command** (`posting.confirm`/`unpostConfirm`), not to the button, so every button running it asks the same thing; the mode that posts on every save is called `onSave` (not `auto`); `__SYS_INTERNAL__` is forbidden inside posting (a service session of `requestedBy` is used instead, so RLS applies through the same code as for a live user). Accumulation **registers** are declared in a `registers` section of `db.json` and become ordinary model definitions; direct writes to a register table are refused by a `dbGateway` middleware. Notification rule: success is ephemeral with a TTL, an error is persisted without one, and only a human-triggered attempt answers at all.
- **Deletion is two steps, and the core owns both** (`drive_root/db/deletionMark.js`, `deleteMarked.js`, `entityStateColumn.js`; section 74 of `АРХИТЕКТУРА_ПРОЕКТА.md`). Every entity gets a service field `deletionMark` (injected at the same two points as `seq`; never declare it). «Delete» in a journal **marks** an entity and only deletes a non-entity outright; real deletion happens in the framework app `apps/deleteMarked`, which checks who still refers to the object and says so in words instead of letting a foreign-key error surface. The governing rule: **only what may be deleted may be marked** — the right to mark is read from the same `entityConfig.immutable` (`deletable`/`when`), never from a second copy of the rule. An object referenced by a closed document (an issued invoice) can't be marked either — it can never be deleted (`deleteMarked.closedReferrers`, decided by the referrer's own `intent`; 16.10.2026: a booking with an issued invoice used to be marked and lost its «ordered» movements). A posted document therefore can't be marked; instead the core offers «unpost and mark», which travels as one queue task (`posting_queue.thenMark`) and sets the mark **in the same transaction** that removes the movements. Two ways to delete are declared per entity — `entityConfig.deletion: { direct, mark }`, both default true — and a **startup reference rule** (`applyReferenceRule`) switches `direct` off for any object another table may point at, whatever the config says. When both remain, the program asks which (`showChoice`); `Del` asks, `Shift+Del` deletes directly. Journals get a 26px icon-only first column combining both states, the deletion mark winning over the posting state.
- **An alert on a document is a movement addressed to a person** (02.10.2026; `drive_root/db/documentAlerts.js`, section 79 of `АРХИТЕКТУРА_ПРОЕКТА.md`, spec `tmp/ТЗ_ОПОВЕЩЕНИЯ_ПО_ДОКУМЕНТАМ.md`). The program regularly knows something important about a document and has nowhere to say it: «invoiced more than ordered», «the guest left and no invoice was issued», «no price found» (which used to vanish with the window it was shown in). One mechanism now answers all three: the document carries its alerts, they show where the person already looks, each has a one-click action, and **they disappear by themselves** when the cause is gone. The app writes **only** «rebuild» and never a deletion — the core removes the old rows in the same transaction that writes the movements, exactly as with register movements, so «new movements, stale alerts» cannot exist. A rule is a named function in a pure factory (`apps/<app>/alerts.rules.js`, next to `posting.handlers.js` — the recompute runs inside posting, i.e. in the forked worker where `init.js` never ran), declaring `severity` (`info`/`warning`/`error` — a core enum that decides colour, order and whether a push goes out), its table, and its occasions: movements (default), `timeDependent: true` + `select` (a daily task — time is not an event in the database and nothing else would notice it), or neither, when the app itself triggers the rebuild (invoice fill warnings). Rewriting is **per rule, matched by order** — an alert has no position key, and rewriting in place is what keeps `pushSentAt`, so a push is never repeated while a returning cause does send one again; the rule's row order must therefore be deterministic. What is stored is the **translation key plus substitutions**, not a finished string: one document is read by people with different languages, and a finished string would belong to whoever last triggered the recompute (a substitution that is itself an interface word travels as `{ i18n: key }`). The action is `{ app, method name, params }` — never a script UID — and it is parsed in one place (`MySpace.alerts.run`) for all three consumers: the form panel, the processing form and the push. «Who else is now stale» is derived from the **register's dimensions** (`relatedFromMovements`): a dimension that references a document says so itself, so an invoice's posting refreshes its bookings' alerts — the posting cascade cannot do it, it only moves forward in time and a booking is older than its invoice. The panel is part of the **form frame** (drawn by the core under the command bar, the layout neither knows nor changes), the journal gets its own 26px column **left of** the state column, and the framework app `apps/documentCheck` («Проверка документов», Service menu) shows every live alert of the organization. A daily summary goes out only when nobody has opened that processing form for `core.alertSummaryIdleHours` (default 24) — if the person looked and knows, there is nothing to remind them of. It is addressed to every active user **except admins** (owner, 15.10.2026: the admin doesn't do this work), each counted under their own RLS, and a new summary **replaces** the unread previous one (notification `tag`) instead of stacking. A booking the owner deliberately won't invoice carries `noInvoiceRequired` («Keine Rechnung erforderlich», tab Zusatz), which silences `booking.notInvoiced`. A form notice that this mechanism replaces gets **removed** (that is how the «invoiced more than ordered» `infoLine` left the booking form): two copies of one sentence on one form is a defect, not a safety net.
- **A field the mechanism owns declares `"service": true`** (`drive_root/db/serviceFields.js`): it stays out of auto-generated forms and auto list columns, but a hand-written layout may still show it. A core write that nobody else may make uses the `coreWrite` token with an explicit field list — never a flag in the context and never a system session (`grant([])` opens nothing and only marks "the mechanism is writing"). `dbGateway.transaction(fn)` makes a block atomic and does **not** open a nested transaction. In `settings.json` the integer type is called `number`, not `integer`.
- **Three process-boundary traps, all invisible without running the app.** (1) `init.js` runs **only in the main process**, so anything the scheduler executes — scheduled tasks and **posting** — must be declared in a pure factory file the forked worker also loads (`scheduler.handlers.js`, `posting.handlers.js`); `entityHooks.register` in `init.js` looks fine on the form and fails in the queue with "handler not registered". (2) the i18n registry is filled by `drive_forms/init.js`, i.e. also only in the main process, so every translation in a worker silently returned the **key** until `drive_root/i18n.js` started loading it lazily (`ensureLoaded`). Signature to keep straight: `tfForSession(key, sessionID, vars)` — a wrong order returns the key rather than throwing. (3) presentation builders registered in `init.js` don't exist in the worker either, so a document created by posting (`ctx.createOnce`) got an empty `name`; builders a worker needs live in `apps/<app>/presentations.js` (a pure factory loaded by both processes, 21.10.2026).
- **A date formed automatically comes from the server, never from the client** (owner, 15.10.2026). One time zone for now — `timeZone` in `server.config.json`, set as `process.env.TZ` in `start()` (the prod container is UTC). The calendar's «Today» asks `GET /server-now`; a typed time travels zone-less and the server turns it into a moment. A document's `date` is a moment and its form shows the time (`applyDocumentDateTime` in uniForm).
- **`default.autoNumber` never proposes a taken number** (15.10.2026): the continuation is the NUMERIC max among numbers with the latest record's prefix (a string `MAX` gave «9» among «1…59»), and `nextFree` skips every number already present in the uniqueness scope (organization, no period, deletion-marked included). A table with no `organizationId` but a `hotelId` (rooms) is numbered per hotel (`numberScope.js`, 18.10.2026 — before that rooms were numbered across all organizations).
- **A selector list is narrowed with `selection.where`**, e.g. `{ "hotelId": "{hotelId}" }` (16.10.2026): `{field}` comes from the table row, else the form field; empty does not narrow; the server accepts plain equalities on model attributes only, RLS on top. A new record's **required** reference with exactly one visible option is filled by the core itself, and tabular-section rows inherit same-named references (organization, hotel) from their owner — app hooks no longer copy `organizationId` into rows. The user snapshot (`getUserBySessionID`) is the full `users` row; it used to be cut to the core model and silently lost `organizationId`. Seasons belong to a hotel (owner, 16.10.2026). Section 80.10 of `АРХИТЕКТУРА_ПРОЕКТА.md`.
- **The UID of an updated record is `whereUid.uidOf(request.where)`, never `request.where.UID`** — under RLS the condition is `{ [Op.and]: [...] }`, so for every non-admin the direct read was empty: saving didn't enqueue posting, a date change didn't re-assign `seq`, the presentation was built from changed fields only (found 15.10.2026; invisible when testing as admin).
- **`Object.keys()` does not see symbol keys, and a Sequelize `where` built from operators is nothing but symbol keys.** `Object.keys(where).length > 0` declared `{ [Op.and]: [...] }` empty, so the project `dbGateway.js` **replaced** it instead of extending it — in the RLS branch that widens the query rather than narrowing it. Test emptiness with `hasConditions` (it also counts `Object.getOwnPropertySymbols`). This is how a register balance "as of a moment" silently became the balance as of today.
- **Database settings are resolved in one place — `drive_root/db/dbSettings.js`** (`DB_SETTINGS_PATH` → `PROJECT_ROOT` → cwd). They used to be read twice with different rules (`sequelize_instance` from cwd, `createDB` from `PROJECT_ROOT`): when those differ, the **migration goes to one database and the server talks to another**, both reporting success. `DB_SETTINGS_PATH` is how you run the same build against a clone without editing the project's own settings file.
- **List columns come from `properties.fields` + `columnOverrides`, not from a `columns` array** — a `DynamicTable` ignores `columns` and opens **empty**, which looks like "no records". A field with `options` but no `inputType` prints the raw value in a cell; `valueIcons` on a column draws an icon per value. Multi-row selection is `properties.multiSelect` with `Ctrl`/`Shift`, read back via `selectedIds()`, and a command can act on it with `"selectionFrom": "<table>"` plus `enabledWhen: { selection: "<table>" }`.
- **Always use `user.UID`, never `user.id`** anywhere in project or framework code. `user.id` returns `undefined` and silently destroys the access-control context.
- **A model may declare its own presentation field** — `entityConfig.presentationField`. Default is still `name`, but `users.name` is the **login** (it's what `login.server.js` matches on), so `users` declares `presentation`. One resolver, `globalServerContext.presentationFieldOf`, feeds both places that build a display string (`getLookupList`, FK columns), with the fallback chain `presentation → name → number → code → UID` (`pickDisplayValue`, mirrored client-side by `pickRecordDisplay`). Server code reading users directly goes through `drive_root/userPresentation.js` (`ATTRIBUTES`/`presentationOf`/`presentationsByIds`) — selecting `['UID','name']` silently degrades the rule to "always the login". Careful with `getUserBySessionID`: it serves a cached **snapshot**, so a presentation added later isn't in it — take the caption from freshly-read data. Section 67 of `АРХИТЕКТУРА_ПРОЕКТА.md`.
- Empty-string values (`""`) are auto-converted to `null` for PostgreSQL in `dbGateway.js` — for FK fields (`references`) **and** nullable fields with validators (`allowNull && validate`, e.g. `email`/`isEmail`, since Sequelize skips validators only for `null`, not `""`).
- **An unfilled date is `0001-01-01`, not `NULL`** (`drive_root/db/emptyValues.js`, "every type has its own empty" — as in classic accounting systems), and the framework injects it as the default for *every* optional date column (`injectEmptyDefaults`). An empty date is a truthy `Date`, so `if (v)` / `{ [Op.ne]: null }` silently treat it as filled — this made every delivery receipt count as "read". Test with `emptyValues.isEmptyDate(v)` on the server, `MySpace.isEmptyDate(v)` on the client, and filter with `{ [Op.gt]: EMPTY_DATE }`. Same reasoning as `money`: the rule must be identical on both sides. Section 61 of `АРХИТЕКТУРА_ПРОЕКТА.md`.
- **`getDefaultValue(level, tableName, uid)` is keyed by TABLE name, not model name** — passing the model name returns `null` silently.
- **Never hardcode VAT/tax rates as numbers.** Rates are data: global reference tables `tax_categories` + `tax_rates` (+ effective-dated links in `tax_category_rates`, `excluded_tables`, seeded in `apps/common/db/defaultValues.json`). Models reference a category (`services.taxCategoryId`, `service_tax_components.taxCategoryId`); the rate is resolved by service date (`resolveRate`/`rateByCode`/`svcRate` in `apps/invoice/forms/invoices.server.js`). A rate reform = one row edit, never a code edit. In document line grids the rate is **picked from `tax_rates`** (`invoice_lines.taxRateId`, `booking_extra_lines.taxRateId`) — no manually typed % anywhere; `invoice_lines.taxRate` keeps the resolved % only as a server-written point-in-time snapshot. A service can split into several VAT rates via `service_tax_components` (`splitMode` = `percent`/`amount`/`remainder`, e.g. breakfast → Speisen 7% + Getränke 19% from 2026-01-01). **The legal *basis* of a rate is data too** — `tax_categories.invoiceNote` (TEXT, `translatable`), never a text in the print template: 0% means either `pass_through` (durchlaufender Posten, § 10 Abs. 1 Satz 4 UStG — Kurbeitrag, not the hotel's turnover at all) or `exempt_longterm` (§ 4 Nr. 12a, stays > 6 months), and writing "steuerfrei" for the former is wrong. Lines therefore snapshot the category too (`invoice_lines.taxCategoryId`), and `onBeforeSave` clears that snapshot when the user overrides the line's rate. Which mode applies to Kurbeitrag depends on the municipality's Satzung — configured per organization/hotel via the service's `taxCategoryId`, not via a separate org setting. Full pricing/VAT rules live in `ПРАВИЛА_ЦЕНООБРАЗОВАНИЯ.md`.
- **A value that has a source is not stored as well** (25.09.2026; section 77 of `АРХИТЕКТУРА_ПРОЕКТА.md`). `bookings.prepayment` is **dead data**: a booking's prepayment *is* the balance of `reg_settlements` for that booking, i.e. the sum of posted cash documents **minus what issued invoices have already applied** (16.10.2026: issuing writes `prepayment −`/`debt −` up to the booking's balance, `writePrepaymentApplied`; storno/correction mirror it) — so the register balance is the *unapplied* remainder (0 after invoicing; that is what an invoice deducts, so a second invoice cannot deduct it again), while the booking's «Anzahlung» field and journal column show **how much was paid** — movements of the money recorders only (`settlementBalance.paidOfBooking`, `registers.balance({ recorderTables })`; 21.10.2026: «0» after the invoice read as «never paid»). A refund reaches the booking through the cash documents' `bookingId` field. A stored field beside it was a second source of one value and would diverge on the first corrected payment. (The column itself was put back on 16.10.2026 as a hidden `service` field, read by nobody, only so that the first start in prod doesn't erase it before `tmp/2026-09-24_anzahlungen_uebertragen` has turned it into cash documents — remove it later, backlog B17.) It is now a **form attribute** `prepaymentPaid` (renamed so as not to collide with the column) computed by the form method `onLoadAttributes` through `apps/common/lib/settlementBalance.js` — one place to answer, because both the booking form and the invoice (`_fillInvoice`, `prepareFromBooking`) ask the same question. The register gained a **`bookingId` dimension**, filled by `apps/cash/hooks/posting.js` only when the payment's source is a booking: the old dimensions (`organizationId`, `clientId`, `settlementKind`) answered "how much has the client prepaid **in total**", which is a different question once a client has two bookings — and joining register → `cash_receipts` → `sourceUID` is not a substitute, as it bypasses `registers.balance`, breaks for other recorders and cannot do "balance as of a moment". Terminology: a *document-basis* is the document another one is made from (for an invoice that's the booking, already held by `invoice_bookings`); the register's dimension is simply **booking**. The «Anzahlung hinzufügen» dialog is gone (21.10.2026, `tmp/ТЗ_ПЛАТЕЖИ_БРОНИ_И_ЖУРНАЛ_ДОКУМЕНТОВ.md`): a NEW booking takes its first prepayment in its own fields (`firstPrepaymentAmount/Method`), and the booking's posting turns them into a receipt ONCE via `ctx.createOnce` + stamp `firstPrepaymentReceiptId` (`posting.creates`; dated the booking's `createdAt` — the moment of entry, § 146 Abs. 1 Satz 2 AO — not the clock; a booking without a room refuses to post, so no receipt). Every other payment lives on the booking's «Zahlungen» tab — the core **document journal** `jrn_cash_documents` (`journals` section in `db.json`: a DB view over several document kinds, kept out of `collectAllModelDefs().models`, read-only, recreated on every start) shown as a subordinate list (`properties.owner: { where, fill }`, `fill` = the form method `fillPaymentDocument`). The same journal is «Geldbewegungen» in the menu. Section 81 of `АРХИТЕКТУРА_ПРОЕКТА.md`.
- **"What is still un-invoiced" is a register balance, and the position key is declared once** (01.10.2026; section 78 of `АРХИТЕКТУРА_ПРОЕКТА.md`, spec `tmp/ТЗ_УЧЁТ_УСЛУГ_ПО_БРОНИ.md`). A booking posts `onSave` (no posting commands, no word «провести» on its form) and writes "ordered" (+1) into `reg_booking_services`; the invoice writes "issued" (−1) from its own frozen lines; the balance answers "what goes into the next invoice", and a **negative** balance is the automatic detection of § 17 Abs. 1 UStG (guest left early) that nobody noticed before. The composition is computed in **one** place for both — `apps/common/lib/bookingServices.js` — and both sides take their positions through the same `collapse`, so the key cannot diverge by construction. `POSITION_FIELDS` = serviceId, bookingRoomId, extraLineId, guestTypeId, taxComponentId, taxRate, taxCategoryId — **references only, never data a human edits**: the unit price and the tax component's *name* were both kept out for one reason, that editing them (a live price list, renaming «Speisen») would move the service to a fresh position whose balance is clean and let it be invoiced twice, silently. The price splits printed lines (§ 14 Abs. 4 Nr. 5) and lives on as a register attribute; the component's printed name lives on as `invoice_lines.taxComponentName`, a snapshot beside the `taxComponentId` the key uses. Register dimensions pointing at a booking's tabular-section row carry **no** foreign key (the rows are deleted on every edit of the booking; an FK would forbid editing it) — and neither do **another document's lines** (`invoice_lines.bookingRoomId`/`extraLineId` are `refersTo`: with ON DELETE SET NULL every booking save nulled them in all its invoices). Removing an FK from `db.json` now also removes it from the database at startup (`migrationUtils.syncForeignKeys`); before 16.10.2026 the migration compared columns only and the constraint stayed. Filling an invoice takes the **current** balance — no queue dependencies, no waiting — and the only guard sits where the human pressed the button: «Создать счёт» refuses on an unsaved booking or `postingState ≠ posted`, while «Заполнить» checks nothing. A journal column for a value that is not in the table is `entityConfig.listAttributes` + the list form's `onLoadListAttributes` (one query per page of rows, never per row).
- **Prices are documents, resolved only via `priceResolver`.** `room_prices`/`service_prices` are gone: accommodation/service prices live in «Price list» documents (`apps/priceList`: `price_lists` + two tabular sections) effective **from the document's `date`**; resolution is a "latest per position" slice (`apps/common/lib/priceResolver.js` — `loadSlice` once per calculation, then in-memory `pickRoomPrice`/`pickServicePrices`). Accommodation price rows reference a **season** (`seasonId` → directory `seasons` + tabular section `season_periods` in `apps/common`), not von/bis dates: a row applies when one of its season's date periods covers the stay date (inclusive bounds). Pricing date mode is an org setting (`pricingDateMode`: booking date vs invoice date, helper `resolveOrgPricingMode`). A stay across a season boundary is priced by the org setting `common.seasonPriceMode` (`arrival` — every night at the arrival-day price, the default and how the real client Seiler invoices; `perNight` — each night at its own season's price, a price change starts a new line; helper `resolveOrgSeasonPriceMode`, 16.10.2026). Invoices are standalone documents (`apps/invoice`: `invoices` + `invoice_bookings` + `invoice_lines`), created from a booking via `prepareFromBooking` → prefilled NEW form (no DB write until the user saves); invoice line grid stores exactly what prints (WYSIWYG — collapse happens at fill time, the print template does not regroup) — with ONE exception, the owner's decision of 21.10.2026: the hotel setting «Gleiche Leistungen mit verschiedenen Preisen zusammenfassen» (`invoice.mergeServiceLines`, on for Seiler) folds, **in print only**, the service lines of one booking with the same service, tax component, rate and category that differ only by price (guest types, two apartments' final cleaning) into one line with unit price «–»; accommodation lines are never folded (`apps/reports/invoice/mergeServiceLines.js`; § 14 Abs. 4 UStG requires quantity and kind, not a unit price — checked against the statute text). Rates are never folded; totals and the per-rate VAT summary are still computed from the stored lines, and the stored lines and the services register are untouched. The collapse key **includes unit price** (`serviceId|component|rate|category|unitPrice`) — without it, age bands of one service merge and the line degenerates to `Menge 1 × whole sum`, breaking §14 Abs. 4 Nr. 5. Line order comes entirely from directories (`services.displayOrder` → `guest_types.displayOrder` → `service_tax_components.displayOrder`), never from hardcoded numbers.
- **Whether a service is counted per guest is the service's own attribute** `services.chargeMode` (`perGuest` / `perBooking`, «Berechnung: je Gast / je Buchung», 16.10.2026), not a guess from the price list: it used to switch on whenever the price list had age-banded prices, and a dog priced by age got multiplied by every guest. `perGuest` = guests × quantity (age band price, or one flat price for all); `perBooking` = quantity as is, flat price only. **Age rules are directory data, not thresholds in code.** Who counts towards the room tariff is `guest_types.roomRateMode` (`included` / `separate` — own price from the price list / `free` — declared free), not `gt.ageFrom >= 6`. Three states, not a boolean, precisely so the "no price" warning can stay silent on declared-free guests: a warning that fires on a legitimate configuration stops being read. Guest-type captions in invoice lines come from the **directory** (`getTranslationLookup('guest_types', orgLang)`), never from `i18n.json` — a caption there would freeze the age bounds the owner edits in the directory. Refilling an invoice never overwrites a non-zero manual `prepayment`/`discountValue`; zero means "not filled" and is pulled from the source bookings.

## Architecture

### Startup flow
`index.js` → `my-old-space`'s `start({ rootPath })` → sets `PROJECT_ROOT`, auto-loads the project-level `dbGateway.js`, starts `memory_store`, then runs the framework's `main_server.js`. Apps are discovered, models merged, DB synced, and each app's `init.js` registers its forms and menu items.

### App structure (`apps/`)
Apps are registered in `apps.json` (project) — the framework also keeps its own registry in `node_modules/my-old-space/drive_forms/apps.json`. Project apps: `common` (shared reference data — organizations, hotels, rooms, services, guest types, clients + `lib/priceResolver.js`), `booking` (the main document form), `priceList` (price-list documents), `invoice` (invoice documents + line calculation), `reports`, `ai_chat`, `formula_editor`, `booking_icons` (applied icon assets). `booking_old` is dead/legacy (unregistered, references dropped tables).

Framework apps worth knowing about (all in `node_modules/my-old-space/apps/`): `tray` (icons in the right of the taskbar — window-independent, unlike taskbar buttons), `notifications` (push-notification stack + the `notifications` table), `settings` (**the single settings form** — all levels in one window, see «Application settings» below), `messenger` (rewritten 06.09.2026 to the current patterns; see «Messenger» below), `imageViewer` (an attachment opened full-screen; `MySpace.open('imageViewer', { url, name })` — one window, the next picture replaces the current one), `documentCheck` («Проверка документов» — one window listing every live document alert of the organization, filtered by severity and document kind; opening it is recorded, and that is what silences the daily summary), `magnifier` (screen magnifier, added 18.09.2026 — no window and no icon, hold the **left** Alt; wheel = zoom, Ctrl+wheel = lens size; off by default via `enabledBySetting`, and a disabled magnifier costs nothing: no key listener and no second copy of the DOM. Section 72). **`fileSystem` is legacy — do not use it and do not build on it** (owner's decision 06.09.2026; it expects `multer`, which isn't a dependency, and stores files on the container filesystem, which no deploy survives). User files go in the DB — see `messenger_attachments`. Details: sections 54–62 of `АРХИТЕКТУРА_ПРОЕКТА.md`.

Window behaviour is declared in the app's `config.json` and shipped to the client as `window.MySpaceAppConfig`: `tray` (icon + tooltip), `hideFromTaskbar`, `preventClose` (the X minimizes instead of closing — so a live form is **not** the same as a form the user can see). A notification's click handler is stored as `appName` + **function name** + params, never as a script UID: `loadScript` issues a fresh UID on every process start.

The canonical app layout (use `apps/booking/` as the reference for everything):
```
apps/<app>/
  init.js                       # ~25-line glue: registers layouts, server scripts, hooks, menu items
  db/db.json                    # model/table/association definitions (no UID field!)
  db/defaultValues.json         # optional seed records with fixed UIDs
  hooks/<name>.js               # entity lifecycle hooks (registered via entityHooks.register)
  i18n.json                     # translations (en + ru minimum; de also used)
  forms/<table>.layout.json     # pure-JSON form layout (no code)
  forms/<table>.server.js       # factory: module.exports = (modelsDB, Utilities) => ({ ...fns })
  forms/<table>.client.js       # client JS; contains the literal placeholder __SERVER_SCRIPT__
```

**Split-file form pattern (required for any form with logic):** `init.js` registers the form's server module with `formMethods.register({ app, subject | form, methods, roles })`, reads the client file and `.replace(/__SERVER_SCRIPT__/g, serverScriptName)` to bind it (the name still comes from `loadServerScript`, which clients call), then `layoutMemory.saveLayout({...})` to register the layout. Never hardcode the server-script name in the client file. Forms are rendered by the generic `uniForm` app driven by the saved layout — you rarely create a per-app UI app.

**A form's ADDRESS is not its SUBJECT** (25.09.2026; full reference: section 76 of `АРХИТЕКТУРА_ПРОЕКТА.md`, spec `tmp/ТЗ_ФОРМЫ_ПРИЛОЖЕНИЯ.md`). The address answers "where is the layout", the subject answers "what does the form work on". `tableName` used to do both, so a window with no table had nowhere to live and apps invented tables that don't exist in the database — six of them did. **Never invent a table name to give a form an address.**
- `saveLayout({ app, subject: { table, kind } })` — a table form; its name is derived canonically (`record:<table>` / `list:<table>`) by `drive_root/formAddress.js` and **must never be written by hand**. `saveLayout({ app, form: 'prepaymentDialog' })` — an app's own window. `app` is the **owning** app (`booking`, `settings`), not `uniForm`; the owner of a table form is looked up by its name (`ownerOfSubjectForm`). The registry key is `app|formName|role|variant`, uniformly — the `main`-variant exception is gone.
- **No subject → no model, no save, no immutability lock, no posting state, no document commands, no unsaved-star.** That follows from the *absence of a subject*, not from `formKind` (which now only names the kind of form). One exception, derived from a fact rather than a second flag: a subject-less form that declares an `onSave` **method** saves itself (settings, backup) and keeps its standard buttons. A named form with no layout registered is a **clear error**, not an autoform — there is nothing to build one from.
- **Form attributes** (`реквизиты формы`) are fields that exist in no table. Declared in the layout node (`type`, `caption`, `required`, `default`). On a subject-less form everything writing to `_dataMap` is one; on a form with a subject they must say `"attribute": true`. They never reach the database — `collectData` skips them and `applyChanges` drops them loudly. Zero is a **value**, not "empty"; `isEmptyDate` is asked only of `date` attributes (it answers "not a date", which is a different question).
- **A server event is a form METHOD** with a conventional name (`onLoadData` / `onLoadAttributes` / `onBeforeSave` / `onSave` / `onAfterSave`) registered via `drive_root/formMethods.js` (`onAfterSave` runs after the header and tabular sections are written; a subject-less form's `onLoadData` receives `params.current` — its own data before the save — so it reloads the record it showed, section 80.12); `onLoadAttributes` is what **computes** a form attribute on a form that has a subject (the record's own fields come from its table; an attribute does not live there) — it runs after the record is read and returns `{ name: value }`, and a name that isn't a declared attribute is dropped and logged, since handing a value to a *record* field that way would be an edit bypassing save; `events` in `saveLayout` are gone, and with them the patch that read events from the main variant. Client-side events stay in the registration as `clientEvents`, at form level. `formMethods` and `serverScriptStore` are two consumers of one core, `drive_root/methodStore.js`. **`'*'` in method roles does not mean "any role"** — write an explicit list.
- Client calls are named: `callFormMethod(app, form, method, params)` / `form.callMethod(...)`; `/server-call` accepts `{ app, form, fn }` beside `{ uid, fn }`. A layout button declares `"method": "execute"` and the core does the rest (confirm, required-attribute check, save-before-command, busy indicator, and parsing `{ error | message | result | close | open }`).
- Open with `MySpace.open('uniForm', { app, form, params })`, or `await MySpace.openModal(...)` to get the dialog's answer (`form.setResult(v)`; closing the window answers `undefined`). Window identity of a named form = address + params, so two prepayment dialogs on **different** bookings are two windows; a modal is never deduplicated. A `recordSelector` may point at a named form (`selection: { app, form }`) when the "directory" it picks from doesn't exist as a table.

Server form functions receive `(params, ctx)` where `ctx = { sessionID, user, role }`. The first RPC argument is always a single `params` object.

### Access control / Row-Level Security
`dbGateway.js` (repo root) registers an **app-level middleware** that runs before every DB operation. It resolves the user *only* from `sessionID` (never trusts a passed `userId`/`role`), then constrains `read/findOne/count/update/delete` to rows the user may see, filtering by `organizationId` / `hotelId` / `userId` (the `required_access_fields` in `app.config.json`).
- `admin` role bypasses filtering.
- Filters are combined with **OR**, not AND: a row is visible if *any* of them matches.
- Tables in `excluded_tables` (`app.config.json`) are skipped — meaning **visible to everyone**, not "admin-only". These are global *public* reference tables. `organizations` is excluded but still gets a special-cased RLS filter by its own `UID`. A system table with no organization (scheduler, backup, db-version bookkeeping) does **not** go here — give it a nullable `organizationId` left `NULL` instead: the startup validator passes and non-admins can't see the rows. Tabular sections need their own access field too — inheriting from the parent doesn't satisfy the validator (see `invoice_lines`).
- **Internal/system calls** must pass `context.sessionID === '__SYS_INTERNAL__'` (`SYSTEM_SESSION_ID`) to bypass RLS — never pass a fake `userId`/`role` instead. Grep `__SYS_INTERNAL__` to audit every bypass. Its scope is a mechanism's *own* bookkeeping tables. Background work acting **on behalf of a user** (scheduler tasks, mailings) must instead run under a real **service session** — a `sessions` row owned by the task's owner — so RLS applies through the same code path as for a live user. Details: section 33 of `АРХИТЕКТУРА_ПРОЕКТА.md`.
- Policy: every non-excluded table **must** have at least one `required_access_field`; this is validated at startup.
- **"Who is in the same boat" is a different question from "what may I read".** RLS answers the second. For the first the core has an extension point, `drive_root/accessScopes.js`: the project registers a resolver (in its `dbGateway.js`) returning opaque scope ids — here the user's organizations, from `user_organizations` via the same cached `getAccessContext`. The core only compares them (`share(a,b)`). Do **not** rebuild this on RLS: `users.organizationId` is often empty because membership lives in `user_organizations`, so an RLS-based answer would be "nobody sees anybody". Framework apps must not name project tables — that's exactly what the resolver is for. Section 69 of `АРХИТЕКТУРА_ПРОЕКТА.md`.

### Messenger (framework app, extended 13.09.2026)
Chats are provisioned by the app, not by users: **everyone gets a chat with the admin**, everyone else only within a shared access scope, and there is **no common chat by default** (owner's decision — a typical client is one or two people). That is a rule about *provisioning*, not a ban: `loadChats` filters nothing by scope, so a chat created by hand across the boundary works.

Translation is per-user and admin-only (`translateIncoming` / `translateLanguage` / `translateOutgoing` at `user` level; `translateApiKey` / `translateModel` at `system`). The messenger has its **own** key and model and its own copy of the provider call (`apps/messenger/lib/translator.js`) — sharing a provider with `apps/ai_chat` today is a coincidence, not a dependency. Three texts, three homes: `messenger_messages.content` is *what was sent* (for the recipient that simply **is** the message — no translation marker is ever shown to them), `originalContent` is what the author typed and is returned **only to the author**, and `messenger_message_translations` holds one translation per (message, language). Incoming messages are translated **before** fan-out so two quick messages can't arrive in the order they happened to finish translating. Every translation gets **context** (14.09.2026): author and readers by name (grammatical gender), the last 8 chat messages, and the translator glossary — **one for the whole system**, no per-organization glossaries (owner's decision; `lib/translationContext.js`, append-only versions in `messenger_translation_contexts`). A weekly scheduler task `messenger.reviewTranslations` (`lib/translationReview.js`, model = system setting `analysisModel`) reviews new translations, **edits the glossary itself** (terms containing a chat participant's name are rejected), verifies it by re-translating the same messages in memory `iterations` times (0 = no verification; the language of a sent translation is NOT stored — the review model names it), stores a review (`messenger_translation_reviews`) and notifies the owner; rollback = "Restore this version" (a new copy). The author's mixing of formal/informal address is the author's choice, never a translation error. Full details: section 70 of `АРХИТЕКТУРА_ПРОЕКТА.md`.

`MySpace.snapshot.serialize()/capture()` takes a picture of the app by **re-rendering the DOM**, not by `getDisplayMedia` (which prompts every session). `serialize` — a copy of the interface detached from both the page and the server — is the reusable part and is meant to outgrow the screenshot button (remote assistance). Section 70.5. A third method, `mirror`, is the same copy kept **live** in this document (shadow DOM, incremental `sync` instead of a rebuild — a rebuild on every change is what made the magnifier stutter once a second); section 72. Client code that needs its own `user`-level setting reads it from `MySpace.settings` (own RPC `settings.mySettings`, never the `/app/loadApps` bundle — it is cached by `role|language`), and the settings form re-reads those personal snapshots on save (`app-settings-changed`), so a per-user app switch takes effect without a page reload.

### i18n
User-visible strings must be translated. Server code: `tForSession`/`tfForSession` (from `drive_forms/globalServerContext`). Static client `.js`: the `__t('key')` marker. Layout/db captions: `{ "i18n": "key" }` objects, resolved at render time. Add new keys to all relevant `i18n.json` files in one pass — languages in use are **en, ru, de, pl** (a missing code silently falls back to `en`). Before deleting a key, grep the whole project *and* `node_modules/my-old-space` for it. **Substitutions are `{{name}}`, with two braces** (`i18n.tf` splits on `'{{'+name+'}}'`): a single brace ships the placeholder to the user verbatim («Выставлено больше, чем заказано: {amount}»). Verify with a run — `i18n.loadI18n(PROJECT_ROOT)` then `tf(key, lang, vars)` in all four languages — not by eye; that run found three such texts of mine plus a long-standing one in `discount_multi_booking_warning`. A single brace is legitimate only where the **client** does its own `.replace('{number}', …)`.

Two distinct translation layers (don't conflate): **(1) `i18n.json`** translates UI strings by key (above). **(2) the `translations` table** (+ `translationMiddleware.js`) translates reference *data* — the `name` value of records in tables with a `translatable: true` field (e.g. `guest_types`, `booking_statuses`); add per-language rows in `apps/common/db/defaultValues.json`. Reference data the *user* enters (services, room names, clients) is single-language by design.

**Documents are in the organization's language, not the user's.** Invoices/reports build their content (incl. line texts) from the org-level setting `project.reportLanguage`, resolved via `resolveOrgReportLang(modelsDB, orgId)` in `apps/common/lib/orgReportLanguage.js` — used by both `reports/init.js` and `booking`'s `_buildInvoiceLines`. Never use `tForSession` (session language) for document content.

**Adding a UI language** is not one row: add it to `languages` (`drive_root/db/defaultValues.json`), add the code to *all* `i18n.json`, add `translations` rows for reference data, add a locale-format mapping (`pl → 'pl-PL'`), then restart (i18n loads into the registry at startup; `languages`/`translations` are re-seeded each startup by `createDB.js`). User language change is only visible after a page reload — the settings form's `onSave` returns `languageChanged` and the client calls `location.reload()`. Any server cache of *translated* values must key by language (see the `getLookupList` `_lookupCache` fix). Full mechanism: section 20 of `АРХИТЕКТУРА_ПРОЕКТА.md`.

### Application settings

**Settings are one core mechanism, not per-app code.** An app declares its settings in
`settings.json` at its root (next to `config.json`); the core collects those files at startup the
same way it collects `db.json`. Three sources, one format: `drive_root/settings/core.settings.json`
(framework, app `core`), `apps/<app>/settings.json`, and `<PROJECT_ROOT>/settings.json` (app
`project` — only for settings the whole solution owns and no single app does, e.g. document
language). Full spec: `tmp/ТЗ_НАСТРОЙКИ_ПРИЛОЖЕНИЙ.md`.

- **A level is a table + record UID**, not a separate mechanism: `user` → `users`, `organization`
  → `organizations`, `hotel` → `hotels`, plus two ownerless ones (`system`, `default`). Levels
  beyond the built-in three are declared by the app that owns the table (`apps/common`). Adding a
  level creates **no tables**.
- **No inheritance between levels.** A setting lives at exactly one level; the only fallback is
  «value → defaults row (admin-editable) → `default` from the file». The defaults row is seeded
  once per key and never overwritten — seeding a value would undo the admin's edit on every restart.
- Values live in one table `settings_values` (JSON column `data`); `userId`/`organizationId` are
  service columns filled by the core for RLS. Read/write only through
  `drive_root/settings`: `getUserSetting` / `getRecordSetting` / `getSystemSetting` /
  `getAppSettings` / `getDefault` and the matching `set*`, plus `getRecordSettingMany` (one
  setting across many records in a single query — use it whenever the question is asked about a
  *list* of people). **No cache** — deliberately.
- **An app can be switched off per user**: it declares `enabledBySetting: { app, key }` in its
  `config.json`, pointing at an ordinary boolean `user`-level setting (`drive_root/appAvailability.js`).
  Off means: no tray icon, `MySpace.open` refuses, and the server refuses too — the core gates
  `/app/call` and `/app/<app>/<method>` in `invokeAppMethod`, while server *scripts* are registered
  by name and know nothing of their app, so the app wraps its own registration in
  `appAvailability.guard(APP, fns)`. The personal list travels by its own RPC
  (`settings.disabledApps` → `MySpace.appAvailability`) because the `/app/loadApps` bundle is cached
  by `role|language`. Section 68 of `АРХИТЕКТУРА_ПРОЕКТА.md`; the role-level switch is section 64.
- The UI is a single form (framework app `apps/settings`): level + record in the header, tabs per
  app. Rights are checked in its RPC — a record-level scope is verified through the same RLS
  (`dbGateway.execute` with the user's session), never by a private copy of the rules.
- Captions are `{ "i18n": key }` and live in the owning app's `i18n.json`; the file never contains
  texts.
- **Interface state is the same table, `kind='state'`** — what the UI remembers between sessions
  (window geometry, last tab, last filter, chosen calendar axis). Keys are free-form and declared
  nowhere; server API `drive_root/settings/state.js`, client `MySpace.state.get/set` (sync read
  from a snapshot fetched by its own RPC — **never put personal data into the `/app/loadApps`
  bundle**, it is cached by `role|language`). Nothing that affects rights, money or calculations
  goes there: the value comes from the client. Admin sees it as one table with «Clear all».
- **Register a layout for everyone as `roles: '*'`, not `'user'`** — `'user'` is a role, and layout
  lookup is exact-match-then-`'*'`. The core now falls back to any registered layout for `admin`,
  but the declaration should still say what it means. Section 66 of `АРХИТЕКТУРА_ПРОЕКТА.md`.

### Scheduled background work
The framework has a **task scheduler** (`node_modules/my-old-space/drive_root/scheduler/`, UI app `apps/scheduler`, tables `scheduler_tasks`/`scheduler_task_params`/`scheduler_runs`). Never write your own `setInterval` for periodic work: declare a task type in `apps/<app>/scheduler.handlers.js` (a pure factory — the file is loaded by **both** the main process and the worker process) and the user creates the task in the UI. Tasks run in a forked worker under a **service session** — a real `sessions` row (`kind='service'`) owned by the task's owner — so RLS applies through the same code as for a live user; `__SYS_INTERNAL__` inside a handler is forbidden. A service session must never work as a login: HTTP takes the session only through `globalServerContext.getSessionIdFromRequest(req)`, which rejects `kind='service'`. Details: section 33 of `АРХИТЕКТУРА_ПРОЕКТА.md`.

### Backup and restore (reworked 11–12.08.2026)
The server is a **staging buffer, not an archive**: prod runs in a container with no volumes, so `docker rm -f` on every deploy destroys its filesystem. Consequences, all deliberate:
- **Settings live in the DB** (`backup_config`, `backup_api_clients`), not in `backupSettings.json` — that file died on every deploy, taking the encryption key and the storage registry with it. Reading stays synchronous via an in-memory cache; async consumers must call `settings.ensureLoaded()` rather than trust the startup warm-up.
- **Only the copy directory stays outside the DB** (`BACKUP_STORAGE_DIR`), together with the maintenance flag and the recovery-password hash: all three are needed exactly when the DB is unavailable.
- **There is no `backup_files` table.** The directory is the source of truth (`drive_root/backup/catalog.js`); metadata comes from the dump's plaintext header, `sha256` from a `<name>.meta.json` sidecar. Run history lives in `scheduler_runs`.
- **Copies are addressed by file name** in both the API and the forms — so the name arrives from outside and becomes a path. It must pass `catalog.safeName()`; never build a path from a client-supplied name directly.
- **System data** (`entityConfig.systemData` + directory `system_data_types`) decides what a full restore may overwrite: by default users, roles, scheduled tasks and backup settings stay *current*. Users merge (backup first, current on top by UID; anyone missing from the current base returns `disabled = true`). Details: sections 45–49 of `АРХИТЕКТУРА_ПРОЕКТА.md`.
- External storage protocol is **MOSBAK2** (`ack` → `delete`); the storage app's task lives in `tmp/backup_external_app/`.

### Events / hooks
- Project `events_handler.js` (repo root) **must** use CommonJS `module.exports = {...}` — `export default` makes the framework silently ignore it. Framework's root `events_handler.js` runs first, then the project's. Key hooks: `onModelsPostCollect` (UID injection), `onDatabasePostInit` (post-sync seeding).
- Entity lifecycle hooks are declared in a model's `entityConfig.hooks` in `db.json` (e.g. `beforeCreate: [{ handler: "booking.onBeforeCreate" }]`) and the handler is registered in the app's `init.js` via `entityHooks.register(name, fn)`.

## Conventions that matter

- **Editing files:** use file-editing tools, not shell redirection/`sed`/`echo >` — keeps changes reviewable/revertible.
- **Editing the framework is the main job** (see "What this is"): fix bugs at their root in the framework base classes, not with patches in `apps/`.
- **Pattern-first:** before writing anything new, copy the matching pattern from `apps/booking/`. Deviating from an established pattern needs explicit justification.
- **Don't paper over framework limitations with naming/data conventions** — fix the framework instead.
- **UI is retro desktop styled (90s look):** reports/documents open *inside* an app window via `MySpace.open('printPreview', { html })`, not `window.open(..., '_blank')`. Build buttons with the `Button` class (`new Button()` → `btn.Draw(container)`), not raw `document.createElement('button')`. New client apps follow the `createInstance` pattern and need `autoStart: true` in their `config.json` plus registration in `drive_forms/apps.json`. Pictures go in the `"type": "image"` control (class `Picture`), not a hand-made `<img>` and not `htmlViewer`. A "stays pressed" toggle is `Button.setPressed` / `RadioGroup` with `appearance: "buttons"` — and note that `Button` writes its relief as **inline** styles, so a CSS rule can never override it. Controls of a form write their value into `form._dataMap` as well as into themselves (the *value*, not the caption); a control that doesn't is a bug — that was the checkbox until 13.09.2026. Section 71 of `АРХИТЕКТУРА_ПРОЕКТА.md`. Document state marks are declarative core elements (section 52.13): `entityConfig.rowTones` colours journal rows and the state field; any layout item may carry `visibleWhen` / `tones`; `type: "relatedLinks"` (a pink line of clickable related records, `link.field` = who refers to me, `link.from` = whom I refer to; visible only when `visibleWhen` holds AND there are links) and `type: "infoLine"` (a static mark such as «Rechnung ungültig»). Never two controls with the same `name`/`data` in one layout — `controlsMap` keeps only the last.
- **No other company's trademark ships with the product.** The framework package is sold, so its code comments, `.md` files and every user-visible string must name the **concept**, not the brand: «как в классических учётных системах», "retro desktop style", "утопленная рамка" — never the product that inspired it. Copying a *principle* is lawful (ideas and interfaces are unprotected: § 69a Abs. 2 UrhG, Directive 2009/24/EC Art. 1(2), CJEU C-406/10); copying *expression* — their documentation text, icons, screenshots, a form's exact layout — is not. So a task to yourself reads "find how mature accounting systems solve this and implement the principle", never "make it like <product>". Naming an OS for a platform fact ("invalid in a Windows file name") stays — that is not a style reference. Full risk analysis incl. vendor duties (Cyber Resilience Act, software product liability, § 379 Abs. 1 Nr. 6 AO): section 6a of `АУДИТ_ПРАВОВОЕ_СООТВЕТСТВИЕ_ГЕРМАНИЯ.md`.
- **Icons are mandatory** on every UI element (button, menu item, table column, toolbar action) via the `icon` property. Catalog: `D:\wohnunger_icons\ICONS_CATALOG.txt`. System icons: `/apps/general_icons/resources/public/16x16/<id>.png`. Applied icons: `/apps/booking_icons/resources/public/16x16/<id>.png`. To add one: create `D:\wohnunger_icons\scripts\icons/<collection>/<id>.py`, run `python scripts/generate_all.py`, update the catalog, then `python scripts/deploy.py` (run Python with `PYTHONIOENCODING=utf-8` — cp1251 consoles die on the `✓` in its output). **Never build the `<img>` yourself** — `MySpace.icon.img(ref, 16)` / `.apply(imgEl, ref, 16)` (inside `UI_classes.js`: `createIconImg`/`applyIcon`). The core picks the file: the size folder if that file exists, otherwise the **`master`** 256×256 one, and adds `srcset` (16→1x, 32→2x) for HiDPI screens. So a new icon is generated **as a master only** — `generate_all.py` produces no per-size files by default, and an icon that genuinely needs hand-tuned sizes declares them in its own script (`SIZES = (32, 16)`) rather than via a run flag. Always PNG-32/RGBA — no alpha means a light rectangle on the grey retro-style button. Which files exist is snapshotted **once at startup** into `window.MySpaceIconIndex` (built by `buildIconIndexCode` in `drive_forms/globalServerContext.js`, shipped as the first line of the `/app/loadApps` bundle), so adding or removing an icon file needs a server restart. Details: section 53 of `АРХИТЕКТУРА_ПРОЕКТА.md`. Replacing an icon file is invisible in the browser for up to a day — icons are served `max-age=86400` with no version in the URL (section 38); clear the cache, and check facts with `curl -D -` before suspecting the code.
- **Window sizing is four core rules, never per-form fixes** (15.10.2026; section 80.9 of `АРХИТЕКТУРА_ПРОЕКТА.md`): a window always stays on the desktop (`Form._keepOnDesktop` after every move/resize/cascade/restore); it is never narrower than the content of ALL its tabs (`measureMinContentWidth`/`getMinWidth`, enforced on drag-resize too); free space reaches tables through every ancestor (`Table._growChain`) — a table with `visibleRows` grows in proportion when its tab has no undeclared «main» table; and heights are re-applied once the size is final (`Form.reapplyTableHeights`: tables first, then tab locks inner-to-outer, measured with growth switched off). Test layouts opened, maximized, restored and maximized again, on a small screen.
- Static assets are only served from `apps/<app>/resources/public/` → URL `/apps/<app>/resources/public/<file>`.
- **German-law compliance is a hard constraint — and the owner's stated top priority is not getting hit with a fine (21.09.2026).** It outranks convenience, schedule and elegance. The working rule: run the legal check on **every** new feature yourself, before building it, without being asked and without asking permission to check; if you find a risk, say so plainly up front, naming the rule and who pays. The owner may have no idea a risk exists — a violation usually looks like a harmless improvement, costs an hour, and raises no suspicion. One case is special: **under KassenSichV the fine falls on the software's author, not on its user** — § 379 Abs. 1 Nr. 4 AO fines whoever *uses* a non-compliant recording system, but **Nr. 6 fines whoever commercially advertises or places one on the market**, up to 25.000 €, whether or not any tax was actually shortened. That is why the «we are not a till» boundary below is the one line in this project that protects *us*. Full audit + action plan (P0–P3): `АУДИТ_ПРАВОВОЕ_СООТВЕТСТВИЕ_ГЕРМАНИЯ.md` (repo root); dev rules: «Правовое соответствие» section in `ИНСТРУКЦИИ_ДЛЯ_AI.md`; technical gap map: section 32 of `АРХИТЕКТУРА_ПРОЕКТА.md`. Core rules: never build features that edit/delete issued invoices (the one exception, owner's decision 13.09.2026: an **admin** with the system setting `core.adminEditsClosedDocuments` bypasses the whole lock via `immutable.adminOverride` — the fix path is back to draft → edit → issue again, since issued invoices print from the archive; and a third closing command next to storno/correction — **«Ungültig»** (`entityConfig.invalidate`, core `drive_root/db/invalidate.js`, button `"command": "invalidate"`): any user, only from `issued`, no counter-document, refused if a storno/correction already exists, printed with an «Ungültig» stamp (same look as «Entwurf», document language) laid over the archive copy by `invalidate.markInvalid` — **but its button was removed from the invoice form on 24.09.2026 (owner's decision); do not put it back.** The core mechanism, the `void` state, the journal tone and the stamp all stay, since already-voided invoices must keep displaying and printing correctly. It is the only one of the three closing commands that produces no counter-document and therefore no reference to the original (§ 31 Abs. 5 UStDV), which is not enough for an invoice already in the customer's hands (§ 14c Abs. 1) — yet users reach for it precisely because it looks like fewer documents for the same result. Storno or correction instead) (GoBD — an issued invoice is changed only by a **counter-document**, of which there are two kinds, both declared in `entityConfig` and both built by `drive_root/db/storno.js`: **storno** (`entityConfig.storno`) cancels in full and sends the source to `cancelled`, **correction** (`entityConfig.correction`) leaves the source valid and carries only the difference (§ 31 Abs. 5 UStDV allows exactly that — «nur die fehlenden oder unzutreffenden Angaben … durch ein Dokument, das spezifisch und eindeutig auf die Rechnung bezogen ist»; a change of the basis *after* the fact — guest leaves early — is § 17 Abs. 1 UStG and is corrected in the period the change occurred, so the correction carries its own date). Never call such a document a «Gutschrift»: § 14 Abs. 2 Satz 4 UStG reserves that word for self-billing. Both are **entirely framework mechanisms**: the core synthesizes the mirror "how it should be" tabular section, computes the difference, and ships both commands as declarative buttons (`"command": "storno" | "correct"`) — an app declares `entityConfig.correction.difference` (which fields make two lines the same position, and where quantity/price/amount live) and writes no correction code at all. The command **writes nothing** (13.09.2026): `storno.prepareCounter` builds the counter-document in memory and the client opens an **unsaved** form (`prefill`/`prefillTabular` + `counterOf`); saving re-checks and stamps the link (`verifyCounter`/`stampCounter` in `uniForm.applyChanges`), and the source goes to `cancelled` only when the storno is **issued** (root `dbGateway` middleware `stornoIssueMiddleware`). Sections 52.2 and 52.10–52.12 of `АРХИТЕКТУРА_ПРОЕКТА.md`; the whole chain — immutability, storno, print archive, hash-chained audit log, and the **form lock** that greys out a closed document — is declared once in `entityConfig.immutable`/`storno`/`auditLog` and enforced by the framework: never re-implement any of it in `apps/`, and a state change with side effects — issuing snapshots the archive and checks §14 — must be listed in `commandStates` so it can't be set by typing in the status field. Section 52 of `АРХИТЕКТУРА_ПРОЕКТА.md`); invoice print template must keep §14 UStG mandatory fields (net **per VAT rate** incl. 0%, `Menge` + `Einzelpreis` as their own columns, Leistungszeitraum, Steuernummer, client address); **verify every legal citation (§/Abs./Satz) against the source before it goes into a printed document** — writing one from memory is how «§ 10 Abs. 1 Satz 5» got printed instead of Satz 4; money is `DECIMAL(12,2)` (rates `DECIMAL(5,2)`) — **all money columns were migrated 24.08.2026**; a `DECIMAL` arrives from the driver as a **string**, so every sum must go through `drive_root/db/money.js` (server) / `MySpace.money` (client) — a hand-rolled `Math.round(v*100)/100` is wrong on the half-cent boundary and diverges from the server. **Every condition over money must survive a negative document**: a storno/correction is all minuses, and `> 0` as "is set", a `[0, base]` clamp, a threshold or a "largest line" compared by value instead of magnitude all fail silently and by large amounts (this is how a storno printed −23,10 € instead of −760,10 €). Column type changes ship in the SAME deploy as the code (the built-in schema migration converts types itself; migrating the DB first prints `NaN` on invoices). Details: section 51 of `АРХИТЕКТУРА_ПРОЕКТА.md`.  new personal-data fields need a legal basis + retention/deletion path (clients get anonymized, never hard-deleted). **Cash and card payments are recorded — that is decided (owner, 21.09.2026), and it is not the red line it used to be.** § 146a AO attaches to the system that *takes* the payment («Erfassung und **Abwicklung**»), not to the word «cash» in a field: a program where payment is booked *afterwards* is a bookkeeping program, like a Kassenbuch, and needs no TSE — which is why nobody demands one of Excel. What must never be added without stopping and warning the user: **a payment receipt (Bon) handed to the guest at the moment of payment, the program being the place where the guest pays, a cash drawer or a Z-report.** Any of the three turns that part into an elektronisches Aufzeichnungssystem and drags in a certified TSE, Belegausgabepflicht, the ELSTER notification and DSFinV-K export. Full reasoning and the owner's wording: §17 of `tmp/ТЗ_ПРОВЕДЕНИЕ_ДОКУМЕНТОВ.md`. **Red lines — stop and warn the user before implementing:** the three till functions just listed, a public B2C booking portal (BFSG/PAngV/§312 BGB), storing individual guest data (Meldeschein §30 BMG, 12+3-month auto-deletion).
